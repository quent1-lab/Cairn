# Cairn — instructions pour Claude

Simulateur d'évolution culturelle et technologique **émergente** : monde infini procédural, humains simulés individuellement, serveur Rust persistant 24/7, client web WASM pixel-art, joueur-divinité (Foi, interventions ambivalentes), Chronique narrative.

**Référence obligatoire : [docs/BRIEF.md](docs/BRIEF.md)** — vision, systèmes, architecture cible, plan en 6 phases avec critères d'acceptation. À consulter avant toute décision de conception.

## Contexte de travail

- Projet d'**apprentissage Rust** + pièce de portfolio (étudiant ingénieur, fort en C/C++/embarqué, Rust en cours d'acquisition).
- Répondre **en français**. Expliquer les idiomes Rust nouveaux dans la réponse (pas en commentaires tutoriels dans le code — les commentaires du code documentent le domaine, pas le langage).

## Règles non négociables (BRIEF §0 et §11)

1. **Émergence stricte** : aucun comportement narratif scripté. Les « âges » sont des étiquettes dérivées, jamais des conditions de déblocage.
2. **Aucune dépendance sans justification** face à une implémentation maison de ~50 lignes.
3. Simple et lisible d'abord ; **optimiser seulement après mesure**.
4. **Déterminisme bit-à-bit** : RNG dérivé de la seed globale (`cairn-core`), jamais d'itération sur `HashMap` dans la simulation.
5. Chaque incrément produit quelque chose de **visible et testable**.

## Architecture

Workspace cible (BRIEF §8) : `crates/{core, worldgen, sim, protocol, server, client}` — `protocol` partagé serveur↔client. Existent : `core`, `worldgen`, `sim`.

`sim` = monde **chunké** (store de tuiles) : le pont entre worldgen (baseline pur, immuable) et l'état mutable à venir. `Tile` (16 o) matérialise le baseline + slots mutables (fertilité, biomasse) ; `Chunk` 64×64 généré à la demande (humidité échantillonnée aux 4 coins partagés → aucune couture) ; `World` = LRU BTreeMap, capacité bornée, éviction sûre car régénérable. Le store sert le **local** ; la vue monde lit le worldgen en échantillonnage grossier (mode carte). **Règle : worldgen reste pur ; l'évolution/mutation vit dans `sim`.**

## Échelle

**1 tuile = 2 m** (échelle humaine : une hutte = plusieurs tuiles, un agent sur une, un village se parcourt tuile à tuile). Source unique : `core::scale` (`TILE_METERS`, `km_to_tiles`, `tiles_to_km`). Tout le worldgen exprime ses tailles en km via ces helpers. Le monde est donc énorme en tuiles (continents ~3000 km ≈ 1,5 M tuiles) — sans coût car procédural/chunké. Le zoom monde↔village est un problème de **rendu (LOD)**, jamais de taille de tuile : proche = sprites/structures, loin = mode carte agrégé.

## Commandes

- `cargo check` / `cargo test` — vérification et tests.
- `cargo run --release -p cairn-sim --example life_demo -- [seed] [années] [agents]` — démo Phase 2 : population lâchée dans un foyer tempéré, rapport mensuel (pop, morts par cause, besoins moyens), verdict face au critère d'acceptation, carte PNG `out/life_<seed>.png` (centrée sur la médiane des survivants).
- `cargo run --release -p cairn-sim --example chronicle -- [seed] [années] [sample_days] [out.csv] [capacité] [agents]` — **banc d'analyse long terme** : foyer tempéré, journalise **tout** (73 colonnes, un échantillon/jour par défaut) dans un CSV — démographie (classes d'âge, sexes, naissances, morts par cause), physiologie (moyennes + pires cas), dérive génétique (6 traits moyens) et culturelle (compétences, savoirs), faune, clans (tailles, stock, formations/dissolutions), tensions, structures, dispersion/migration (boîte englobante, centroïde), perf. CSV vidé à chaque échantillon (une exécution interrompue reste analysable). Défauts : seed 42, 50 ans, /1 j, `out/chronicle_<seed>.csv`, 16384 chunks, 40 agents. ~15 tps → **50 ans ≈ 8 h** (à lancer en tâche de fond).
- Client : `cargo run --release -p cairn-client --example preview -- <couche> <km>` rend le canvas en PNG (vérif sans navigateur). Bundle web : `crates/client/build.sh` (nécessite `wasm-bindgen-cli` — voir note d'env).
- `cargo run --release -p cairn-worldgen --example map_png -- <seed> [tuiles/pixel]` — rend une image PNG par couche du pipeline dans `out/` (`_alt`, `_temp`, `_hum`, `_bio`) + % de terres émergées ; 2ᵉ arg = zoom (petit = gros plan). Toujours en `--release`.
- `cargo run --release -p cairn-worldgen --example analyze -- [nb_seeds] [onde_continent] [sea_bias]` — vérifs statistiques : connexité des masses terrestres + preuve du rain shadow (humidité par barrière au vent).
- **git : uniquement via Git Bash** — absent du PATH PowerShell. Les commits sont gérés par Claude (demande explicite de l'utilisateur), messages en français, style conventional commits.

La suite naturelle est la **Phase 5 — L'Étincelle** (arbre technologique en données, exposition/pression/insight, diffusion, commerce longue distance).
- **Incrément 9 (« les structures ») — le dernier, avec de vrais effets de jeu** : module `sim::structures` + registre `Sim::structures: Vec<Structure>` (clairsemé, côté `Sim`, **jamais un champ de `Tile`** malgré le champ `structure` anticipé par le BRIEF §2.3 — même leçon d'échelle qu'à l'incrément 7). **Trois types, trois effets réels** (contrairement aux incréments 6-8, mesurés mais sans conséquence) : **Hutte** → chaleur passive (`felt += HUT_WARMTH_C` pour un membre à portée d'une hutte de **son** clan, sans avoir à s'arrêter pour s'abriter) ; **Grenier** → relève le plafond du stock commun (`+GRANARY_STOCK_BONUS`, appliqué au report du stock) ; **Palissade** → la tension inter-clans (incrément 6) monte à `PALISADE_TENSION_FACTOR` de son rythme contre un clan protégé. **Construction émergente, à deux étages** (jamais « si taille N, bâtir ») : (1) `structures::plan` (passe quotidienne) mesure trois *pressions* par clan — froid moyen des membres, remplissage du stock, tension max avec un voisin — et fixe `Clan::desired` = la structure non bâtie dont la pression dépasse le plus largement son seuil (rapport pression/seuil, échelle commune, pas de priorité fixe) ; un clan au chaud, stock vide, sans voisin ne désire rien. (2) `TaskKind::Build(StructureKind)` (candidat de plus dans `brain::decide`) : un adulte, au foyer, aux besoins couverts (on bâtit repu), propose de bâtir la structure désirée **si le stock commun peut la payer** — la construction **consomme le stock** (le coût du BRIEF), le premier arrivé bâtit, un seul exemplaire par type et par clan. Pas de compétence de construction pour l'instant (déféré ; le coût en stock suffit à gater). **Découverte de calibrage majeure, corrigée** : la première version liait chaque structure à un `ClanId` fixe et supprimait celles des clans disparus (`prune_orphans`) — vérifié empiriquement (`client_render`, log quotidien étendu d'un compteur `struct`), **0 structure après un an** : les clans de la scène par défaut changent d'identité sans cesse (fission/dissolution, `ClanId` neuf pour ~les mêmes gens), et chaque changement détruisait leurs bâtiments. **Correctif qui fait interlock avec l'incrément 7** : une structure appartient à **qui contrôle sa tuile** (`social::claim_at`), réévalué chaque jour (`structures::maintain`) — un clan qui se reforme au même endroit *hérite* du campement ; une structure que plus aucun clan ne revendient est *abandonnée* et tombe en ruine après `STRUCTURE_DECAY_DAYS` (30 j). Re-vérifié : sur un an, les structures s'accumulent (3-4 en milieu d'année) et une palissade survit jusqu'à la fin. Dans cette scène tempérée à deux clans en concurrence, la palissade domine (tension récurrente) ; les huttes n'apparaissent pas (personne n'a froid en tempéré — elles émergeraient en climat froid), les greniers demandent un stock proche du plafond. **Tests** (mécanisme, pas scène complète — même raison qu'aux incréments précédents) : `plan` (froid→hutte, stock plein→grenier, aucune pression→rien, déjà bâti→plus désiré) ; effets purs (chaleur limitée au clan et à la portée, compte des greniers) ; `maintain` (reprise par le clan qui tient le lieu, ruine après le délai d'abandon) ; exécution de `Build` (financée par le stock, pas de doublon). **148 tests workspace verts** (112 sim + 25 worldgen + 8 core + 3 client), aucune régression.
- **Incrément 8 (« le chef »)** : `social::elect_chiefs`, BRIEF §5.1 « chef : `max(oratoire × prestige)`, contestable ». Deux facteurs mesurés séparément, jamais un rôle attribué directement. **Oratoire** (`skills::Skills::oratory`) : une compétence de plus, même patron que cueillette/chasse (plafond conditionné par un trait — `sociabilité`, déjà le trait qui pousse `TaskKind::Socialize`, réutilisé plutôt qu'un nouveau trait inventé pour l'occasion — et courbe saturante par la pratique) ; sa pratique n'a pas besoin d'une tâche dédiée : `social::encounter` (la même passe qui renforce les liens d'affinité toutes les 4 h) fait déjà pratiquer un peu d'oratoire à quiconque a eu au moins une conversation cette passe — un candidat de moins à ajouter au softmax de `brain::decide`. **Prestige** (`agent::Prestige`, nouveau composant) : contrairement aux compétences, ne sature ni ne décroît — une réserve d'estime accumulée à vie. Un seul déclencheur pour cet incrément : ce qu'un agent a effectivement rapporté à son clan (`TaskKind::BringSurplusHome`) grossit son prestige du même montant que le stock reçoit (conservation testée). Un compagnon qui a nourri le groupe pendant des années garde son ascendant même le jour où il chasse moins bien qu'un jeune loup — voulu, pas un oubli de décroissance. `elect_chiefs` (dernière étape de la passe quotidienne, après `detect_clans`/`update_relations`) désigne, pour chaque clan, le membre qui maximise `oratoire × prestige` — égalité départagée par le plus petit `AgentId`, même convention que `claim_at` (incrément 7), testée indépendante des cas d'égalité. **« Contestable » n'est pas une mécanique à part** : le calcul est refait en entier chaque jour à partir des scores du jour (même principe que la détection de clan elle-même, recalcul complet, jamais d'état modifié incrémentalement) — la position change de mains dès qu'un autre membre dépasse le titulaire, sans code de contestation dédié. `Clan::chief: AgentId` (provisoire à la construction du cluster — le plus petit membre pour un clan neuf, l'ancien chef reporté pour un clan qui continue — toujours recalculé par `elect_chiefs` juste après dans la même passe, jamais lu entre les deux). **Portée limitée** comme les incréments 6 et 7 : être chef ne déclenche encore aucun comportement (pas de privilège, pas d'autorité) — mesurable et testable, prêt pour un futur système. **Tests** : parler pratique l'oratoire (contre-épreuve : un agent isolé n'en gagne jamais) ; le chef élu maximise le produit, pas un facteur seul (témoin : immense prestige mais oratoire nul → score nul, ne l'emporte pas) ; égalité stricte départagée par le plus petit id. **139 tests workspace verts** (103 sim + 25 worldgen + 8 core + 3 client), aucune régression.
- **Incrément 7 (« le territoire diffusé »)** : `social::claim_at`. L'incrément 2 avait fait de `Clan::home` un point qui *attire* ; BRIEF §5.1 demande un vrai « champ d'influence diffusé sur la grille ». **Décision d'implémentation qui s'écarte du texte initial du projet** (qui anticipait un champ `Tile::claim` écrit en dur) : au vu de l'échelle réelle du monde (1 tuile = 2 m, un territoire de rayon `RESIDENCE_RADIUS_TILES` ≈ 2250 tuiles couvre à lui seul ~16 millions de tuiles), **écrire** cette valeur dans chaque tuile de ce disque, chaque jour, pour chaque clan, aurait été incompatible avec l'architecture chunkée/LRU (`Tile` reste à 16 octets, l'éviction ne sait sauvegarder que deux champs mutables — `world::ChunkDelta`) — l'anti-pattern exact que le chunking existe pour éviter (BRIEF §8.2). `claim_at((position, clans) → Option<ClanId>)` est donc une **fonction pure calculée à la demande**, dans l'esprit du worldgen lui-même (baseline pur, jamais stocké), pas une mutation de `Tile` : le champ existe au sens mathématique — interrogeable en tout point — sans jamais être matérialisé sur la grille. **La diffusion** : chaque clan projette une force `membres × (1 − distance/RESIDENCE_RADIUS_TILES)` (même rayon que le territoire-attracteur et la co-résidence — un seul seuil partagé par toute la Phase 4), nulle au-delà. La tuile revient au clan de force maximale en ce point si elle est positive, sinon elle est libre. **Aucun seuil de population lu directement** : un clan plus peuplé projette naturellement plus loin dans les zones de recouvrement, conséquence arithmétique du facteur `membres` (même philosophie que la borne de fission) — pas une règle spéciale. Égalité stricte départagée par le plus petit `ClanId`, **testée indépendante de l'ordre du slice** (pas de dépendance à un ordre d'itération accidentel). Aux confins de deux territoires qui se chevauchent, la frontière est la même zone que celle où `update_relations` (incrément 6) détecte une tension — les deux mécanismes lisent la même géométrie sans être couplés entre eux. **Portée limitée à ce que le critère demande** : ce champ ne pilote encore aucun comportement (rien ne le consulte pour se déplacer, chasser, ou refuser l'accès) — il est mesurable et testable, prêt pour un futur incrément (structures : où a-t-on le droit de bâtir ?) sans changement supplémentaire à ce module. `Sim::claim_at(x, y)` en wrapper ergonomique. **Tests** : foyer revendiqué par son propre clan ; hors de portée → libre ; le plus proche l'emporte à effectif égal ; le plus peuplé l'emporte à distance strictement égale ; égalité stricte départagée par id, vérifiée dans les deux ordres du slice. **135 tests workspace verts** (99 sim + 25 worldgen + 8 core + 3 client), aucune régression.
- **Incrément 6 (« les relations inter-clans »)** : `social::update_relations`, appelée juste après `detect_clans` dans la passe quotidienne. Répond directement au dernier critère BRIEF §9 non rempli. **Le mot clé du critère est *observable*, pas *scripté*** : la tension n'est jamais décidée, seulement mesurée, exactement comme la détection de clan elle-même. Pour chaque paire de clans dont les foyers sont assez proches pour se disputer un territoire (`CONTACT_RADIUS_TILES = 2×RESIDENCE_RADIUS_TILES` — deux fois le rayon de territoire, la distance en dessous de laquelle deux zones se touchent structurellement), on somme le gibier réel (`fauna::Herd::population`, la même notion que pour la chasse) dans un rayon autour du point médian des deux foyers, rapporté au nombre de membres des deux clans réunis. **Une seule règle, sans cas spécial** : rare (`SCARCITY_PER_CAPITA=3,0`, estimation de premier ordre non minée sur une scène multi-jours, à affiner si contredite) ET en contact → la tension monte (nudge saturant, `TENSION_RISE_RATE=0,12`, même idiome que les liens sociaux) ; sinon (hors de contact, ou ressource abondante) → elle redescend (`TENSION_DECAY_RATE=0,08`). `ClanRelations::tension` (`BTreeMap<(u64,u64), f32>`, clé normalisée comme `SocialGraph::bonds`) est **reconstruite en entier chaque jour** à partir des seuls clans qui existent encore — un clan qui s'efface (fission, effondrement) emporte ses tensions avec lui sans code de nettoyage dédié, exactement le même principe de reconstruction totale que `Clan::home`/`sim.clans`. **Portée délibérément limitée** : aucune notion de conflit, guerre ou combat n'est ajoutée ici (`force`/`agressivité` restent en attente depuis la Phase 3) — c'est strictement ce que le critère BRIEF demande, l'observabilité d'une tension mesurée, pas sa conclusion narrative (Phase 5+, Chronique). **Tests au niveau du mécanisme** (deux `Clan` synthétiques injectés dans `sim.clans` + un seul troupeau réel via `spawn_herd`, même patron qu'aux incréments 3 et 5) : (1) deux clans en contact avec un troupeau minuscule (10 têtes/20 bouches, sous le seuil) → la tension monte strictement chaque jour pendant 20 j, sature sous 1,0, dépasse 0,6 ; (2) contre-épreuve ressource abondante (1000 têtes) entre les mêmes clans en contact → tension nulle après 20 j ; (3) contre-épreuve distance (mêmes clans, même troupeau rare, mais hors de `CONTACT_RADIUS_TILES`) → tension nulle après 20 j — les deux conditions du critère (voisinage ET rareté) comptent vraiment, aucune seule ne suffit. **130 tests workspace verts** (94 sim + 25 worldgen + 8 core + 3 client), aucune régression.
- **Incrément 5 (« la fission »)**, fait avant l'incrément 6 ci-dessus : `social::resolve_cluster` — jusqu'ici, un groupe connexe qui échouait le test de cohésion (densité insuffisante pour sa taille, voir l'incrément 1) était simplement **abandonné** : un clan trop nombreux se dissolvait au lieu de se scinder. Écrire « si `members.len() > N`, couper en deux » aurait été l'anti-pattern que le BRIEF §11 interdit — la taille n'est **jamais** lue directement. À la place : quand un groupe échoue la validation prise en bloc, on cherche s'il cache deux (ou plus) sous-groupes plus densément liés en **relevant progressivement le seuil de lien** utilisé pour la recherche de structure (`FISSION_THRESHOLD_STEP=0,05`, jusqu'à `FISSION_MAX_THRESHOLD=0,95`) — la coupure d'un dendrogramme à seuil (single-linkage), une technique connue, pas une heuristique inventée pour l'occasion. **Le seuil qui mesure la cohésion ne bouge jamais** (`BOND_THRESHOLD`, le même pour tout le monde) : seul le seuil de *recherche* de la coupure monte. Si le sous-graphe des liens les plus forts se sépare en plusieurs morceaux, chacun est réévalué **récursivement par exactement les mêmes règles** que n'importe quel clan (taille ≥8, cohésion, co-résidence) — `validate_cluster` ne sait pas qu'il valide une fille plutôt qu'un clan ordinaire. Un groupe trop petit pour produire deux clans viables (`< 2×MIN_CLAN_SIZE`), ou qu'aucun seuil ne sépare jamais proprement (il ne reste que des individus isolés), s'efface — le comportement d'avant cet incrément, préservé comme cas limite. **Aucun changement à la réconciliation d'identité** : une fille qui retrouve la majorité des membres de l'ancien clan **hérite** de son `ClanId` (le mécanisme de persistance de l'incrément 1 s'applique tel quel), l'autre est un `Formed` ordinaire — une fission se lit donc « le clan continue, amoindri, + un nouveau clan apparaît », sans code dédié. **Tests au niveau du mécanisme** (`resolve_cluster`/`validate_cluster` appelés directement avec un graphe et des positions synthétiques, pattern déjà établi à l'incrément 3 — construire un vrai scénario de fission par simulation complète serait lent et fragile) : (1) deux sous-groupes de 10 densément liés entre eux mais reliés par seulement 2 ponts plus faibles — pris en bloc (20 membres), la densité est sous le seuil de cohésion (0,26 < 0,28) ; `resolve_cluster` les sépare en deux clans de 10, sans membre perdu ni dupliqué ; (2) contre-épreuve : un simple anneau de 20 (une seule force de lien partout, aucune sous-structure) ne fissionne jamais artificiellement — il finit par se réduire à des individus isolés, tous trop petits, et s'efface entièrement. **127 tests workspace verts** (91 sim + 25 worldgen + 8 core + 3 client), aucune régression.
- **Historique des incréments (incrément 1, « l'émergence »)** : module `sim::social` — graphe d'affinités et détection émergente de clan (BRIEF §5.1, §9). **Le principe tenu** : le clan n'est jamais scripté, seulement détecté. Deux mécanismes purement observationnels : (1) **graphe d'affinités** (`SocialGraph`, `BTreeMap<(u64,u64), f32>` non orienté) — chaque rencontre à portée de conversation (même rayon que `memory::exchange_knowledge`, passe toutes les 4 h) renforce un lien par nudge saturant (`skill::practice`), plus vite entre parenté directe (mère/enfant, fratrie) ; relâchement quotidien multiplicatif, oubli sous seuil ; **plafond de liens par agent** (`MAX_BONDS_PER_AGENT=15`, hypothèse de Dunbar) ne gardant que les liens **mutuellement** dans le top de chaque côté. (2) **Détection quotidienne** (`social::daily`, cadencée comme `demography::daily`) : composantes connexes du graphe filtré au seuil de lien (**union-find maison** à compression de chemin + union par rang, ~35 lignes — pas de dépendance, BRIEF règle n°2), retenues comme clan si taille ≥8 **et** densité interne ≥ seuil de cohésion **et** ≥70 % des membres à moins d'un rayon de résidence du centroïde (éclaireurs tolérés). **La borne de taille (« fission ») est une conséquence arithmétique, pas un cas spécial** : la densité maximale atteignable par un groupe de `n` membres avec un degré plafonné à `MAX_BONDS_PER_AGENT` décroît en `1/n` — au-delà d'une certaine taille, aucune topologie ne peut plus satisfaire le seuil de cohésion. **Persistance d'identité** : recalcul complet chaque jour, un clan garde son `ClanId` s'il retrouve un groupe partageant la **majorité** de ses membres dans les deux sens ; sinon il s'efface (`ClanEventKind::Dissolved`) — c'est ce mécanisme, et lui seul, qui donne « un clan affamé s'effondre » (testé en tuant tous ses membres, sans aucune règle « si affamé, dissoudre »). `ClanMembership` (composant `Option<ClanId>`, resynchronisé en bloc chaque jour) à côté des autres composants d'agent. **Calibrage mesuré** (scène 24 agents, seed 42) : `ENCOUNTER_GAIN=0,15`, `COHESION_THRESHOLD=0,28`, `RESIDENCE_RADIUS=4,5 km` (70 % des membres) — valeurs choisies en observant la distribution réelle des liens et des distances, pas devinées (piège rencontré : `km_to_tiles` vaut `km×500`, pas `km×1000` — un rayon « de 2 km » ne faisait que 1 km). **Limite connue à cet incrément** (résolue à l'incrément 2 ci-dessous) : rien dans les comportements Phase 2-3 ne fait *revenir* un agent vers son clan (`Socialize` ne rejoint que le plus proche congénère, pas un clan précis) — la population diffuse sans borne (plusieurs km en quelques semaines, mesuré jusqu'à 8 km/85 j sur la scène de test), si bien qu'un clan formé peut se dissoudre de lui-même par pure dérive spatiale plutôt que par un vrai effondrement. **Tests** : formation sans règle explicite (témoin positif 24 agents resserrés vs témoin négatif dispersé à 4 km d'écart, même effectif), dissolution par disparition des membres, déterminisme bit à bit de l'historique de clans. 115 tests workspace verts (79 sim + 25 worldgen + 8 core + 3 client), aucune régression.

  - **Incrément 2 (« le foyer ») fait** : `Clan::home` — le centroïde des membres, déjà calculé par `detect_clans` pour le test de résidence — devient le **territoire**, au sens le plus simple qui vaille : pas encore un champ diffusé sur la grille (ça viendra avec les structures, qui touchent enfin les champs `structure`/`claim` de `Tile`, BRIEF §2.3), juste un point qui **attire**.   - **Incrément 3 (« le grenier ») fait, puis affiné pour le réalisme du dépôt** : `Clan::stock` — réserve alimentaire commune, mêmes unités que `Physiology::hunger` (BRIEF §5.1 : « stock commun, ressources mises en commun »). **Dépôt** : une chasse réussie (`sim::execute`, bras `Hunt`) nourrit une quantité fixe (`HUNT_NUTRITION`, une bête tuée, pas une portion calibrée) — ce qui dépasse la faim du moment, auparavant perdu dans le `.max(0.0)`, est **porté** par le chasseur (nouveau composant `Carrying(f32)`, présent sur chaque agent depuis sa naissance/son lâcher) plutôt que déposé sur-le-champ. **Question de l'utilisateur qui a corrigé le tir** : la toute première version déposait le surplus instantanément, où que soit le chasseur — incohérent avec le retrait, qui exige déjà d'être au foyer. Corrigé : un nouveau candidat `TaskKind::BringSurplusHome` (même patron softmax que `ReturnToClan`) ramène le chasseur chargé vers le foyer de son clan, où le dépôt a lieu à l'arrivée (conservation stricte, testée). Si le chasseur meurt ou ne rentre jamais (un besoin plus pressant l'emporte durablement), le surplus porté est simplement perdu — aucun code dédié pour ce cas, la dérive suffit. La cueillette, elle, n'alimente pas le stock : son prélèvement est déjà borné à ce que la faim réclame (`wanted = hunger.min(bite)`), structurellement pas de surplus à y capter. **Retrait** : candidat `TaskKind::EatFromStock` dans `brain::decide`, même garde que le désespoir alimentaire de l'errance (rien de local ne répond — ni cueillette ni gibier) — le stock n'est pas un porte-monnaie magique, la cible est le foyer du clan, il faut y être pour puiser. **Confirmé (même question)** : un agent ne peut puiser que dans le stock de **son propre** clan — `EatFromStock` ne cible jamais que `clan_views.get(&clan_id)` où `clan_id` est l'appartenance propre de l'agent, jamais celle d'un voisin ; aucun accès croisé possible par construction, pas de garde à ajouter. **Conservation stricte** à l'exécution, dans les deux sens : `taken = stock.min(hunger)` au retrait, dépôt intégral de `Carrying` au retour — la faim/le stock, ou le stock/le portage, bougent du même montant, testé bit à bit. **Plafond** `STOCK_CAP_PER_MEMBER = 3.0` (quelques portions de réserve par membre, pas un grenier sans fond), appliqué au report post-boucle plutôt qu'au dépôt (c'est là que le nombre de membres est déjà sous la main). Un clan qui s'efface perd son stock avec lui — pas de redistribution codée pour un cas déjà rare (BRIEF §11 : pas de règle spéciale sans besoin mesuré). **Tests** au niveau du mécanisme (`execute` appelé directement — accessible depuis `mod tests` du même fichier) plutôt qu'un scénario complet : un clan injecté à la main ne survivrait pas à la prochaine détection de minuit, qui le remplacerait par ce que le graphe social détecte réellement — trois tests couvrent la chaîne complète (chasse → `Carrying` sans toucher au stock ; `BringSurplusHome` → stock à parts égales ; `EatFromStock` → faim/stock à parts égales). **118 tests workspace verts** (83 sim + 25 worldgen + 8 core + 3 client), aucune régression.

Un troupeau qui tombe sous `HERD_MIN` (4 têtes) est **supprimé** (`doomed`, despawn), et rien d'autre ne fait apparaître de *nouveaux* troupeaux après le lancement (seule la fission > 90 têtes en crée) — l'observation exacte déjà notée à l'« Observation de calibrage » ci-dessus, jamais corrigée jusqu'ici. **Mécanisme** : chaque jour, 15 % de chance de tirer un site candidat près d'un humain pris au hasard (1 à 4 km), giboyeux (biomasse ≥ 40, seuil déjà utilisé par `scenario::populate`) et loin (≥ 3 km) de tout troupeau existant — sinon rien. **Auto-limitant sans garde explicite** : une zone déjà giboyeuse n'a simplement jamais de site valide, pas besoin d'écrire « seulement si le gibier est rare ». **Gardé — deux versions.** V1 : `hunted_head > 0` (dans `Sim::step`) — l'immigration ne repeuple que ce qui a déjà été chassé par un humain. Corrigeait bien la régression initiale (3 tests de clan cassés : un scénario délibérément sans faune, `herd_grid=0`, recevait quand même du gibier dont la chasse dispersait la population avant qu'un clan ait le temps de se former — `un_clan_emerge_sans_regle_explicite`, `un_clan_s_efface_quand_ses_membres_disparaissent`, `le_territoire_stabilise_la_derive_apres_formation`). **Mais fausse dans deux cas, découverts en rejouant le scénario exact de l'utilisateur avec les logs quotidiens ci-dessous** : (1) si les prédateurs seuls vident le gibier avant qu'un humain ait jamais réussi une chasse, `hunted_head` ne monte jamais ; (2) le client permet de lancer une scène à **densité de gibier nulle** (`herd_grid=0`, champ « Densité de gibier » de l'onglet Paramètres) — sans le moindre troupeau, aucun humain ne peut jamais chasser, `hunted_head` reste nul indéfiniment, l'extinction redevient permanente. C'est le cas (2) que l'utilisateur a effectivement rencontré. **V2 (actuelle)** : `pub allow_fauna_immigration: bool` sur `Sim`, **vrai par défaut** (le monde est censé être habité), désactivé **explicitement** par les scènes de test contrôlées (`sim::tests::scenario_setup` et le témoin dispersé de `un_clan_emerge_sans_regle_explicite`) plutôt que déduit indirectement de l'état de la simulation. **Test de non-régression dédié** (`une_scene_sans_gibier_initial_finit_par_en_recevoir`) : un `Sim` construit directement (donc `allow_fauna_immigration` à sa valeur par défaut), sans le moindre troupeau initial, finit par en recevoir un — ce test aurait échoué avec la garde V1. **Outillage ajouté au passage** : `client_render` accepte un 4ᵉ argument `log_every_days` (0 = silencieux) qui imprime une ligne d'état par jour simulé (population, gibier/troupeaux, prédateurs/meutes, `hunted_head` cumulé, clans) — sert à diagnostiquer une trajectoire sans deviner. **Mesuré** (`client_render`, seed 42, scène par défaut, `herd_grid=2`) : gibier 0 → 41 têtes à 150 j, 0 → 1002 têtes à 1 an. **125 tests workspace verts** (89 sim + 25 worldgen + 8 core + 3 client).

  - **Immigration de prédateurs — la symétrie manquante (corrige l'emballement de la faune, 2026-07-23)** (`fauna::daily_predator_immigration`). **Révélé par le banc `chronicle`** (run tempéré long, arrêté à l'an 2, voir la commande `example chronicle`) : les prédateurs s'éteignaient au ~6ᵉ mois par boom-bust de Lotka-Volterra (normal), mais **ne revenaient jamais** — l'immigration ne réensemençait que le gibier (`daily_immigration`, ci-dessus), pas les meutes. Sans prédateur, le gibier explosait sans frein (**495 → 66 800 têtes, 22 → 800 troupeaux en 2 ans**, écroulant les tps). **Correctif symétrique** : les prédateurs suivent leur proie, donc ils réapparaissent **près d'un troupeau** (`herds` en ancre, pas les humains) plutôt qu'ailleurs, loin des meutes déjà là (`PREDATOR_IMMIGRATION_MIN_PACK_DISTANCE_TILES=3 km`, auto-limitant comme le gibier), à `PREDATOR_IMMIGRATION_CHANCE_PER_DAY=0,06` (plus bas que les 0,15 du gibier : les prédateurs sont rares, et il ne faut pas sur-réprimer la proie ; assez pour réparer une extinction en ~quelques semaines avant l'explosion). `is_valid_pack_site` (pure, sans test de biomasse — un carnivore ne broute pas, la proie est garantie par l'ancre) + `daily_predator_immigration`, salt 1011, appelés dans le même bloc « 4 bis » que le gibier sous `allow_fauna_immigration`. **Mesuré après correctif** (`chronicle` 3 ans) : le cycle proie-prédateur **oscille durablement** — gibier borné **69 ↔ 1085** (au lieu d'exploser), prédateurs **11 ↔ 160** (jamais éteints durablement, chaque creux suivi d'un rebond). **4 tests** (site valide sans meute voisine ; meute proche invalide / lointaine non ; zone giboyeuse sans meute finit par recevoir un prédateur ; sans gibier aucune immigration de prédateur). **Constat de dispersion non bornée des non-affiliés** relevé au même run, **non corrigé** (voir mémoire `cairn-calibrage-run50ans`).

  - **Calibrage (banc `example calibrate`)** : lâche la population dans des foyers de climats différents (tempéré / frais / froid, cherchés par `scenario::find_home_where`) sur plusieurs seeds, mesure la mortalité **par cause** + le **% de temps passé à s'abriter** (`Sim::shelter_ticks`). Le **% d'abri croît avec le froid** (0 % en tempéré → 2-15 % en froid) : le critère « s'abritent quand il fait froid » est **prouvé et gradué**. La survie au froid **bascule autour de 0 °C** : au-dessus → survivable avec abris et quelques morts de froid ; en dessous (taïga -0,6 °C) → extinction par hypothermie, **assumée et réaliste** (sans feu ni vêtements, personne ne passe un hiver de taïga — la pression qui motivera le feu en Phase 5). (Bug corrigé au passage en Phase 2 : `populate` débordait le nombre d'agents visé — `break` n'échappait que la boucle interne.)

    **Recalibrage post-Phase 3 (mémoire spatiale)** : sur 3 seeds × an complet, **6/9 scénarios gardent une mortalité partielle**, l'extinction en taïga froide reste cohérente, mais **2/9 (seed 7, tempéré et frais) tombent à zéro mort** — contre une robustesse sur les 3 seeds avant la mémoire. Diagnostic confirmé **émergent et attendu**, pas un bug : un agent qui *connaît* une source fiable (repli mémoire dans `brain::decide`, voir incréments 2-3 ci-dessous) ne meurt plus de soif à proximité de son foyer — exactement l'effet voulu du savoir. Pas de correctif forcé (violerait la règle d'émergence stricte, BRIEF §0.4) ; à surveiller si la Phase 4+ a besoin d'une pression plus dure. **Bug réel trouvé et corrigé à cette occasion** : `calibrate.rs` calculait `dead = placed - population()` (`usize`) — dès qu'une population **grandit** par les naissances (Phase 3), la soustraction **débordait** silencieusement (`18446744073709551606` affiché comme nombre de morts). Corrigé en `dead = sim.deaths.len()` (déjà le bon calcul dans `life_demo.rs`). Leçon : toute stat dérivée de `placed - population()` est devenue invalide dès que la population peut croître — vérifier ce pattern si on l'introduit ailleurs (protocole/serveur, Phase 6).
